### 一、是什么
C++异常处理是C++语言提供的一种错误处理机制，允许程序在运行出现错误时，通过 `try`、`catch`和`throw`三个关键字将错误信息传递回调用栈，进行异常处理。
简单来说，当程序检测到无法处理的错误时，可以 **抛出** 一个异常对象；程序的控制流会沿着调用栈向上回溯，直到找到能够 **捕获** 并处理这个异常的代码；如果始终没有找到，程序将终止。
C++的异常处理机制支持异常的重新抛出、自定义异常体系，并且标准库提供了以 `std::exception` 为基类的异常类层次结果。

---
### 二、为什么需要它
#### 2.1 传统错误处理方式的缺陷
在C语言中，错误处理主要依赖两种方式：`assert` 终止程序，或返回错误码。这些方式存在明显问题：
- **容易忽略错误检查**：调用方可能忘记检查返回值，导致程序在错误状态下继续运行，产生不可预知的结果
- **错误信息不充分**：仅凭一个错误码难以传递足够的上下文信息，调试困难
- **代码可读性差**：大量的错误码检查逻辑混杂在正常业务逻辑中，干扰代码的清晰度
#### 2.2 异常处理的核心优势
- **强制处理错误**：未捕获的异常会终止程序，迫使开发者必须正视错误
- **分离错误检测与处理**：异常可以在检测错误的代码与处理错误的代码之间建立明确的分离，中间函数可以透明地让异常传播
- **自动资源清理**：异常抛出后，栈展开机制会自动销毁沿途的所有局部对象，确保资源被正确释放
- **信息丰富**：异常是对象，可以携带详细的错误描述和上下文信息

### 三、核心语法与分类
#### 3.1 三个核心关键字
| 关键字     | 作用                                               |
| ------- | ------------------------------------------------ |
| `try`   | 标记一个可能抛出异常的代码块，其中的代码被称为"保护代码"                    |
| `throw` | 抛出一个异常对象。当问题出现时，程序通过 `throw` 来发出异常信号             |
| `catch` | 捕获 `try` 块中抛出的异常并进行处理，可以有多个 `catch` 分支来匹配不同类型的异常 |
#### 3.2 异常的类型
C++ 中可以抛出 **任意类型** 的对象 -- 基本类型、指针、类对象均可。但在实际工程中， **强烈建议抛出继承自** `std::exception` **或其派生类的对象**，以便统一处理
标准库提供异常类体系 (定义在 `<stdexcept>` 中)：

| 异常类                     | 描述                 |
| ----------------------- | ------------------ |
| `std::exception`        | 所有标准异常的基类          |
| `std::runtime_error`    | 运行时错误 (如溢出、文件打开失败) |
| `std::logic_error`      | 逻辑错误 (程序员失误导致)     |
| `std::out_of_range`     | 容器越界访问             |
| `std::invalid_argument` | 参数无效               |
| `std::length_error`     | 容器过长引发的错误          |
#### 3.3异常抛出与捕获规则
- 异常是通过 **类型** 来匹配的，`throw` 表达式的值本身没有实际意义， **类型才是决定哪个**`catch` **被激活的关键**
- 被选中的 `catch` 是调用链中 **与异常类型匹配且距离抛出位置最近** 的那一个
- `catch(...)` 可以捕获任意类型的异常，但无法获取具体的错误信息，通常用作最后的"兜底"
- 派生类异常可以被基类 `catch` 捕获 -- 这一特性在实际项目中非常实用
- **异常的重新抛出**：在 `catch` 块中使用 `throw;` (不带表达式) 可以将当前捕获的异常原样重新抛出，传递给外层的 `catch` 处理。注意 `throw e;` 会拷贝异常对象，可能导致派生类信息丢失 (切片问题)

### 四、典型应用场景
#### 4.1 构造函数失败
构造函数没有返回值，无法通过返回错误码来报告失败。抛出异常是构造函数报告失败的标准方式。
#### 4.2 文件操作与资源管理
文件打开失败、内存分配失败等场景，异常配合 [[RAII | RAII(资源获取即初始化)]] 可以确保资源不会泄露
#### 4.3 容器越界访问
标准容器的 `at()` 方法在索引越界时会抛出 `std::out_of_range` 异常
#### 4.4 网络请求与外部服务调用
网络超时、服务不可用等运行时错误，适合用异常向上传递错误信息
#### 4.5 大型项目的统一错误处理
在实际项目中，通常会定义一套继承自统一基类的一场体系，各模块抛出不同类型的派生异常，外层通过捕获基类来同意标准

### 五、完整示例
``` c++
#include <iostream>
#include <stdexcept>
#include <string>

// 自定义异常类
class MyException : public std::runtime_error {
public:
    explicit MyException(const std::string& msg)
        : std::runtime_error(msg) {}
};

// 可能抛出异常的函数
int divide(int a, int b) {
    if (b == 0) {
        throw MyException("除数不能为零");
    }
    return a / b;
}

// 使用 RAII 管理资源
class FileGuard {
public:
    explicit FileGuard(const std::string& filename) {
        m_file = fopen(filename.c_str(), "r");
        if (!m_file) {
            throw MyException("打开文件失败: " + filename);
        }
        std::cout << "文件打开成功" << std::endl;
    }

    ~FileGuard() {
        if (m_file) {
            fclose(m_file);
            std::cout << "文件关闭成功" << std::endl;
        }
    }
private:
    FILE* m_file;
};

// 演示异常重新抛出
void processData() {
    try {
        FileGuard fg("data.txt");
        int result = divide(5, 0);
        std::cout << "5 / 0 = " << result << std::endl;
    } catch (const MyException& e) {
        std::cerr << "局部处理: " << e.what() << std::endl;
        throw; // 重新抛出，让上层处理
    }
}

int main() {
    try {
        processData();
    } catch (const std::exception& e) {
        std::cerr << "顶层捕获: " << e.what() << std::endl;
        return -1;
    } catch (...) {
        std::cerr << "未知异常" << std::endl;
        return -1;
    }

    return 0;
}
```
**运行结果**：
``` txt
文件打开成功
文件关闭成功
局部处理: 除数不能为零
顶层捕获: 除数不能为零
```

### 六、性能与注意事项
#### 6.1 性能特点
- **正常路径零开销**：在没有抛出异常的情况下，`try-catch` 块几乎不产生运行时性能损耗
- **异常路径代价高昂**：抛出异常并执行栈展开比简单的返回错误码要昂贵很多
- **二进制体积增加**：即使从不抛异常，编译器也需要为每个局部对象生成栈展开信息，这增加了二进制文件的大小，在某些嵌入式环境下可能达到 5% 到 15% 的体积膨胀
- **优化受限**：异常处理会抑制编译器某些优化，如寄存器分配和指令重排
#### 6.2 关键注意事项
1. **析构函数绝不能抛出异常**：如果在栈展开过程中析构函数又抛出异常，`std::terminate` 会立即调用，程序终止。析构函数应默认标记为 `noexcept`
2. **构造函数抛出异常时析构函数不会被调用**：因为对象从未完全构造完成。因此构造函数中获取的资源必须使用 [[RAII]] 包装器(如只能指针) 管理
3. **按引用捕获**：应使用 `catch(const std::exception& e)` 而非传值捕获，以避免对象切片和不必要的拷贝
4. **捕获顺序**：多个 `catch` 分支按书写顺序匹配，**派生类异常必须在基类之前捕获**，否则派生类永远无法被匹配到
5. `noexcept`**关键字**：C++11引入 `noexcept`，用于声明函数不会抛出异常。如果一个类型移动构造函数未标记 `noexcept`，`vector` 在重新分配内存时会选择拷贝而非移动，造成严重的性能损失
6. **异常安全保证**：编译异常安全代码需要遵循三个基本保证级别：
	- **基本保证**：不泄露资源，对象保持有效状态
	- **强保证**：操作要么完全成功，要么完全回滚，不改变状态
	- **不抛出保证**：操作永不失败(`noexcept`)

### 七、与相关特性对比
#### 7.1 异常 vs 错误码
| 对比维度       | 异常              | 错误码          |
| ---------- | --------------- | ------------ |
| **错误强制处理** | 未捕获则终止程序        | 容易被忽略        |
| **错误信息**   | 可携带丰富的上下文(对象)   | 仅一个数值，信息有限   |
| **代码可读性**  | 错误处理与业务逻辑分离     | 错误检查充斥在代码中   |
| **性能**     | 异常路径开销大，正常路径零开销 | 每次调用都需要检查返回值 |
| **控制流**    | 隐式非局部跳转         | 显式返回，控制流清晰   |
| **构造函数**   | 可以正常报失败         | 无法返回错误码      |
#### 7.2 异常 vs `noexcept`
`noexcept` 不是错误处理机制，而是一种 **承诺** -- 告诉编译器和调用者该函数不会抛出异常。它的价值在于：
- 编译器可以据此进行优化，省略栈展开信息
- 标准库容器 (如 `vector`) 会根据移动操作是否为 `noexcept` 来决定使用移动还是拷贝，影响性能
#### 7.4 异常 vs C++17 `std::optional` / C++23 `std::expected`
这些是现代C++中"将错误作为值"的方案，代表了一种不同于异常的设计哲学 -- 控制流完全显式，调用者必须处理错误。这种方式在性能敏感和嵌入式领域更受青睐。

---

### 总结
C++的异常处理是一把 **双刃剑**。它通过 `try`、`throw`、`catch` 三个关键字，提供了一种将错误检测与错误处理相分离的结构化方式，配合 [[RAII | RAII]] 可以实现自动资源管理，是构造函数失败等场景下的首选方案
然而，异常处理也带来了不可忽视的成本：二进制体积增加、优化受限、控制流隐性化导致代码理解困难。正因如此，C++社区对异常的态度存在明显分歧 -- Google、LLVM等团队选择禁用异常，而Boost、Bloomberg等则坚定使用
**实践建议**：
- **在应用程序层**，异常通常是合理的选择
- 在 **性能敏感的底层或嵌入式系统**，需谨慎评估
- 无论选择与否，[[RAII | RAII]] 是必须掌握的，它是C++资源管理的基石
- 析构函数 **必须** 是 `noexcept` 的
- 捕获异常时 **按引用捕获**，避免切片
